# Етап 8: колекція Postman

`lab5.postman_collection.json` містить експорт користувача з Postman у форматі Collection v2.1. Після експорту абсолютний шлях до власного JPEG замінено на переносимий `output/custom/432.jpg`. Успішні запуски користувач підтвердив у розмові; надані знімки початкових помилок, успішного ручного PUT і картинки /418 збережено в `report/evidence/`. Знімків підсумків двох успішних запусків Runner поки немає серед отриманих матеріалів.

## 1. Запусти окремий сервер

У PowerShell у корені проєкту:

```powershell
$postmanCache = './test-output/postman-manual-' + [guid]::NewGuid().ToString('N')
node main.js -h 127.0.0.1 -p 3001 -c $postmanCache
```

Це нова порожня тека кешу. Сервер на порту 3000 і його картинки не змінюються. Залиш це вікно відкритим. Якщо порт 3001 зайнятий, вибери інший і зміни змінну `baseUrl` у колекції.

## 2. Імпортуй колекцію та вибери файл

1. У Postman натисни **Import** і вибери `postman/lab5.postman_collection.json`.
2. У змінних колекції перевір `baseUrl = http://127.0.0.1:3001`.
3. У налаштуваннях **Working directory** вибери корінь цього проєкту — теку, де лежить `main.js`. Шлях `output/custom/432.jpg` у JSON відносний до цієї теки.
4. Відкрий запит **05. PUT власної картинки**, перевір **Body → binary**. Якщо Postman не знаходить файл, вибери локальний `output/custom/432.jpg` вручну й збережи запит. Це локальний запуск, завантажувати файл у хмару не потрібно.

Пояснення робочої теки та відносних шляхів: [документація Postman](https://learning.postman.com/docs/getting-started/installation/settings/working-directory).

## 3. Запусти Runner двічі

Запусти всю колекцію через **Run collection / Runner**, одна ітерація, всі 11 запитів у початковому порядку. Якщо є параметр збереження відповідей, увімкни його для перегляду результатів. Потім запусти ще раз із тим самим сервером і кешем.

| № | Запит | Очікування |
|---|---|---|
| 01 | DELETE /200 | 200 або 404: підготовка |
| 02 | DELETE /432 | 200 або 404: підготовка |
| 03 | GET /200 | 200, image/jpeg, джерело http.cat |
| 04 | GET /200 | 200, image/jpeg, джерело cache |
| 05 | PUT /432 | 201, власна картинка |
| 06 | GET /432 | 200, image/jpeg, джерело cache |
| 07 | DELETE /432 | 200 |
| 08 | DELETE /432 | 404 |
| 09 | GET /432 | 404, текстова відповідь, немає заголовка джерела |
| 10 | POST /200 | 405, Allow: GET, PUT, DELETE |
| 11 | DELETE /200 | 200: очищення після запуску |

Для кожного запиту є тести статусу й Content-Type; для кожного GET — також перевірка заголовка X-Image-Source. Тести використовують стандартний `pm.test()` у середовищі Postman. Його синхронні тестові функції не є колбеками Node.js-сервера: у `main.js` єдиним колбеком залишається async-обробник createServer. Нових npm-залежностей немає.

Перші два DELETE роблять запуск відтворюваним, навіть якщо попередній запуск перервався. Наприкінці /200 видаляється, а /432 уже видалено кроком 07. Тому під час другого повного запуску очікуються ті самі статуси й джерела; час може відрізнятися. Крок 09 залежить від реальної відсутності картинки /432 на http.cat. Якщо джерело зміниться чи буде недоступним, перевірки покажуть фактичну поведінку.

Скрипти запитів 03 і 04 зберігають `remoteTimeMs` та `cacheTimeMs` у змінні колекції й виводять їх у Postman Console. Порівняй також час у результатах Runner. Тест не вимагає, щоб кеш завжди був швидшим: це вимірювання, а не гарантований поріг.

Про перевірки та результати Runner: [документація Postman](https://learning.postman.com/docs/tests-and-scripts/write-scripts/test-scripts/).

## 4. Підготуй фактичні матеріали для звіту

- Запиши версію Postman.
- Зроби знімок результатів першого та другого запусків Runner, де видно пройдені й невдалі перевірки.
- Запиши час запитів 03 і 04 окремо для кожного запуску; не підставляй час із curl.
- Після Runner відкрий у браузері `http://127.0.0.1:3001/418` і `http://127.0.0.1:3001/404`, перевір картинки й зроби знімок екрана.
- Щоб побачити власне фото, ще раз виконай PUT із запиту 05, потім відкрий `http://127.0.0.1:3001/432`. Після повного Runner власна картинка вже видалена, тому спочатку потрібен PUT.
- Експортуй перевірену колекцію з Postman як Collection v2.1 у `postman/lab5.postman_collection.json`. Перевір, що шлях до binary-файла переносимий і немає приватних даних.

Експорт і знімок картинки /418 отримані. Успіх після виправлення binary-файла підтверджено користувачем. Для завершення доказової частини звіту потрібно додати знімки двох успішних Runner-запусків та їхні фактичні вимірювання часу. На початковому невдалому запуску видно GET із джерела 124 мс та з кешу 3 мс; ці числа не підміняють час успішних запусків.

## Що вже перевірено автоматично

Синтаксис 11 Post-response скриптів перевірено як JavaScript. JSON прочитано, а HTTP-послідовність виконано двічі через curl із фактичними URL, методами, заголовками й binary-файлом із колекції. Після отримання експорту з Postman повторно перевірено об'єктний формат URL та відносний шлях до фото: ще 22 запити без невідповідностей. Для відтворення є команда:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\postman\check-sequence.ps1
```

Це додаткова перевірка HTTP, вона не замінює Collection Runner і не виконує Postman-скрипти. Скрипт запускає окремий сервер на порту 3001; якщо він зайнятий ручним сервером, додай до команди `-Port 32162`. Політика Bypass діє лише для поточного процесу PowerShell. Робочий кеш не використовується.

Фактичний результат: **22 запити, 0 невідповідностей**. SHA-256 відповіді GET після PUT збігся з власним JPEG в обох запусках.

| Запуск curl | GET із джерела, мс | GET із кешу, мс |
|---|---:|---:|
| 1 | 153,455 | 2,384 |
| 2 | 70,215 | 2,007 |

Ці числа отримані через curl `time_total`, не Postman. Повні команди, заголовки й результати записані в локальний `test.txt`.
