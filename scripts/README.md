# Перевірки помилок і цілісності даних

Запуск із кореня проєкту у Windows PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-errors.ps1
```

`Bypass` діє лише в цьому процесі PowerShell; постійну політику виконання скриптів команда не змінює. Потрібні встановлені залежності (`npm.cmd ci`), Node.js, curl.exe із підтримкою `--parallel` та вільні локальні порти 32159, 32160, 32161.

Сценарій створює окремі теки в `test-output/`, запускає власні процеси й зупиняє їх у `finally`. Робоча тека `cache/` не використовується. Команди curl.exe, відповіді, хеші та результати дописуються в локальний `test.txt`; старі результати зберігаються. Артефакти навмисно залишаються для перевірки й не потрапляють у Git.

Перевіряються:

- PUT/GET із порівнянням SHA-256 та DELETE наявної й відсутньої картинки;
- порожній PUT, тіло понад 20 MiB зі звичайною та chunked-передачею;
- перерване завантаження: без створення нового або пошкодження попереднього файла;
- неправильні шляхи, спроби виходу за межі кешу та метод POST;
- помилки читання, заміни та видалення: тека замість очікуваного файла;
- 20 паралельних PUT/GET до одного коду, перевірка повноти відповідей та очищення тимчасових тек;
- помилки джерела: 503, 404, HTML замість JPEG, порожнє тіло JPEG, таймаут, відмова з'єднання;
- робота кешу після відключення джерела та працездатність сервера після помилок.

Для збоїв джерела скрипт створює копію поточного `main.js` в `test-output/` і замінює **лише** URL `https://http.cat/` на адресу локального тестового сервера. Робочий `main.js` не змінюється. У цій частині значення заголовка `http.cat` означає гілку завантаження з підставленого джерела; це не звернення до справжнього http.cat. Тестовий сервер використовує лише http, fs/promises і один async-обробник createServer.

Тестова велика картинка має початок JPEG і нульові байти в кінці: вона перевіряє збереження байтів, а не декодування зображень. curl може надсилати Expect: 100-continue, тому скрипт перевіряє останній статус HTTP, пропускаючи проміжний 100.

Під час виконання етапу 7 до виправлення шість із десяти паралельних GET отримали порожні або неповні дані. Після виправлення фінальний запуск виконав 50 HTTP-запитів і 148 перевірок без невідповідностей. Попередні невдалі запуски й причини виправлень також залишені в `test.txt`.

## Пояснення змін для захисту

`saveImage()` спочатку записує дані в унікальну тимчасову теку всередині кешу, а після завершення переносить готовий файл через `rename()`. Попередня картинка не обрізається на початку запису. Тимчасові файли прибираються у `finally`. Використовуються функції [fs/promises](https://nodejs.org/api/fs.html#fspromisesrenameoldpath-newpath).

`activeRequests` зберігає проміс поточного запиту для кожного коду. Наступний запит до того самого коду чекає його завершення. Це запобігає одночасній заміні файла на Windows і гонкам GET/PUT/DELETE. Запити до інших кодів можуть працювати паралельно. `handleImageRequest()` викликається напряму, не передається як колбек. Єдиний колбек програми залишається async-обробником `http.createServer()`.

PUT приймає до 20 MiB включно. Якщо межу перевищено, накопичені частини звільняються, решта потоку дочитується без збереження, а клієнт отримує 413. Це дозволяє завершити HTTP-відповідь без передчасного руйнування сокета асинхронним ітератором. Файл кешу не змінюється.

## Межі перевірок

Черга діє в межах одного процесу Node.js; кілька серверів зі спільним кешем не координуються. Повільний PUT затримує інші запити до того самого коду. Ліміт стосується одного тіла PUT, а не сумарної пам'яті всіх одночасних запитів. JPEG не декодується й не перевіряється повністю. Аварійне завершення процесу може залишити тимчасову теку; стійкість до вимкнення живлення не перевірялася. Помилки запуску на зайнятому порту не входять у ці HTTP-перевірки.
